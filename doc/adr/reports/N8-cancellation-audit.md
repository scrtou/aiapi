# N8 · 取消检查点普查报告

> 状态：**已完成**（2026-08-07） 类型：只出报告，不改代码
> 目的：为 N6「停机时取消在途请求」提供是否实施的事实依据
> 取证方式：全库 grep + 关键调用链逐段阅读，非测试源文件 149 个

---

## 1. 结论先行

**N6 维持不实施。** 取消机制当前不是「覆盖不全」，而是**结构上无法到达阻塞点**。
在 Provider 接口打通取消传递之前，任何「停机时 cancel 全部 token」的改动都只会
产生日志，不会缩短一秒停机时间。

**新增结论（本次普查发现，此前未记录）**：真正的停机延迟主因不是取消缺失，
而是 **29 个上游 HTTP 调用中有 21 个没有显式超时**。这是比 N6 优先级更高的问题。

## 2. 取消机制现状

### 2.1 全库分布

| 位置 | 性质 |
|---|---|
| `SessionExecutionGate.h:30-59` | `CancellationToken` 定义（`atomic<bool>` + `cancel()` / `isCancelled()`）|
| `SessionExecutionGate.h:134` | 抢占旧会话时 `slot->currentToken->cancel()` —— **唯一的 cancel 调用方** |
| `SessionExecutionGate.h:277-288` | Guard 转发 `getToken()` / `isCancelled()` |
| `GenerationService.cpp:221` | 检查点 1 —— 调用 Provider **之前** |
| `GenerationService.cpp:347` | 检查点 2 —— 调用 Provider **之后** |

**引用该机制的非测试文件仅 3 个。** 此前记录的「全库仅 2 处检查点」经复核**属实**。

### 2.2 两个检查点保护了什么

```
:218  sink.onEvent(startEvent)
:221  ← 检查点 1
:222 ─┐
      │  125 行：Provider 调用、重试、CodexRooCompat 严格重试
      │  期间无任何取消检查
:346 ─┘
:347  ← 检查点 2
```

两个检查点**夹住了整个耗时区间，但不进入其中**。它们能捕获的只有
「请求在排队等 Gate 时被抢占」这一种情况 —— 而那种情况本来也不阻塞停机。

### 2.3 结构性阻断

```cpp
// src/apipoint/APIinterface.h:28
virtual provider::ProviderResult generate(session_st& session) = 0;
```

**接口签名里没有 token 参数**，`session_st` 也不携带 token。这意味着：

> Provider 实现（chayns / nexos / openai）在物理上无法查询取消状态。

这就是为什么补检查点这件事**不能靠「多加几个 if」解决** —— 得先改接口。

## 3. 五类阻塞边界逐项裁定

| # | 边界 | 现状 | 可中断性 | 裁定 |
|---|---|---|---|---|
| 1 | **上游 HTTP** | 29 处 `sendRequest`，仅 8 处带显式超时 | ❌ 21 处依赖 Drogon 默认超时 | **最高优先级，见 §4** |
| 2 | **chayns 轮询** | `while (now < requestDeadline)`，循环条件只看时钟 | ❌ 用 `sleep_for`，不可唤醒 | 需 token 传入，随阶段 3 |
| 3 | **重试退避** | `chaynsapi.cpp` 4 处 `sleep_for`（514/865/956/1026）| ❌ 不可唤醒 | 归入 N7 |
| 4 | **SSE 输出** | `IoLoopResponseStream::send()` 返回 `bool` | 🟡 **有信号但未接线** | 见 §5 |
| 5 | **DB 操作** | 全部 `execSqlSync`（SessionDb 20+ 处、chaynsThreadDb 10+ 处）| ❌ 同步阻塞 | 不改，见下 |

**DB 不改的理由**：单条 SQL 执行时间在毫秒级，不构成停机瓶颈；
改成异步会波及所有 DbManager 的调用方，成本远超收益。**明确排除，不留待办。**

### 3.1 一个反例：accountManager 做对了

`accountManager.cpp:448` 的 `backgroundSleep()` 用的是 `wait_for(谓词)` 而非 `sleep_for`，
停机时 `notify` 可立即唤醒（:1482 / :1687 / :2452 / :2462 四处长睡眠均走此路径）。

**这是仓库里唯一正确的可中断等待实现**，N7 替换其余 sleep 时应以它为模板，
不要另起炉灶。

但同文件内仍有 8 处裸 `sleep_for`（:1520 / :1771 / :1793 / :2030 / :2044 / :2049 / :2070 / :2436），
**同一个文件里两种做法并存** —— 说明当初是打补丁而非统一治理。

## 4. 本次普查的主要发现：HTTP 超时缺口

29 个 `sendRequest` 调用中 **21 个未传超时参数**，分布：

| 文件 | 无超时调用点 |
|---|---|
| `nexosapi.cpp` | :493 / :866 / :939 / :1029 / :1084 |
| `chaynsapi.cpp` | :217 / :485 / :1160 / :1226 / :1411 |
| `accountManager.cpp` | :1077 / :1112 / :1201 |
| `OpenAiProvider.cpp` | :53 / :288 |

带超时的 8 处取值也不统一：`30.0` / `300.0` 混用，无常量定义。

**为什么这比 N6 重要**：一个挂死的上游连接会占住 worker 线程直到默认超时，
停机时 `join` 必须等它。**取消到不了那里，但超时能。** 超时是唯一在
当前架构下就能生效的止损手段，且改动是纯参数化的、风险极低。

> **新增待办 N10 · HTTP 超时统一**（0.5 天）
> 定义 `kUpstreamTimeout` 常量族（快速接口 / 生成接口分档），
> 21 处补齐，8 处改用常量。随阶段 3 Provider 归一一并做，届时调用点已收敛。

## 5. SSE 断连信号未接线

`IoLoopResponseStream.h:127` 处 `if (!stream_->send(chunk))` —— **返回值已经能表达
「客户端断了」**，但当前只用于跳过后续写入，没有回传给 Gate 去 cancel token。

这是五个边界里**唯一不需要改接口就能接线**的：客户端断连时让 sink 通知 Gate
取消对应 token，检查点 2（:347）即可生效，提前结束无人接收的生成。

> **新增待办 N11 · SSE 断连回传取消**（0.5 天）
> 收益明确（省掉无人接收的上游 token 消耗），改动局限在 sink 与 Gate 之间。
> 但依赖 §3 的 token 可达性，故仍排在阶段 3 之后。

## 6. 对 N6 的最终处置

| 项 | 判定 |
|---|---|
| N6 原设想 | 停机时遍历 Gate slots 调用 `cancelAll()` |
| 技术可行性 | ✅ `cleanup()` 已遍历 `slots_`（O(n)，`maxIdleSlots=1000`），加 `cancelAll()` 是小改 |
| 实际收益 | ❌ **接近零** —— token 传不到阻塞点，cancel 后线程照样卡在 `sendRequest` / `sleep_for` |
| **裁定** | **不实施。** 降级为阶段 3 的子项，待 Provider 接口带上 token 后重新评估 |

**N6 不是被推迟，是被证伪。** 原始判断「设标志即可取消」建立在
「检查点覆盖阻塞区间」这一未经核实的假设上，普查证明该假设不成立。
